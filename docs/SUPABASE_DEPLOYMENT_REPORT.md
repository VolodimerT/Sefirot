# SEFIROT CORE 2.2 — частная база и подготовка выгрузки

Дата: 2026-09-28. Организация: `volodimerkulchinskiy@gmail.com's Org`; проект: `sefirot-core` (`kxqpwgwihtjmqlcxgfxp`); регион: `eu-central-1`. До создания пользователь подтвердил предложение $0/месяц. Сведения о тарифе могут меняться; платный тариф не включался.

## Изменения и проверка

1. Создан новый проект; Postgres 17.6 ответил на SQL-запрос, до развёртывания схемы `sefirot` в нём не было.
2. Миграция `20260928165034_create_private_sefirot_core_v2_1` создала 22 таблицы в схеме `sefirot`.
3. Анализаторы выявили изменяемый `search_path` одной функции и девять внешних ключей без индекса. Миграция `20260928165221_secure_mutation_trigger_and_index_foreign_keys` зафиксировала `search_path` функции и добавила девять индексов. Снимок итоговой схемы для **пустой новой базы**: `schema/supabase_core.sql`.
4. Повторный SQL-запрос: **22/22** таблицы с RLS, **22/22** триггера блокировки UPDATE/DELETE, девять дополнительных индексов на нужных столбцах, настройки функции `search_path=""`. У ролей `anon`, `authenticated` и `service_role` нет права `USAGE` на схему или `SELECT` из её таблиц. Все таблицы пусты.
5. После исправления предупреждений об изменяемом пути функции и неиндексированных внешних ключах больше нет. Security Advisor выдаёт INFO `rls_enabled_no_policy` для 22 таблиц: намеренно закрытая клиентская политика. Performance Advisor выдаёт INFO `unused_index` для 14 индексов: таблицы пустые, по реальному профилю запросов их ещё нельзя оценить.
6. Транзакционный пробный запрос временно вставил команду, проверил отказ вставки матча с отсутствующей второй командой (FK) и отказ UPDATE через `reject_mutation`. Затем запрос намеренно завершился исключением; повторный SELECT подтвердил `teams_count=0`, `matches_count=0` и отсутствие пробной записи.
7. Миграция `20260928181739_sefirot_private_append_only_ingest_role` добавила отдельную роль `sefirot_ingest` с **NOLOGIN**, SELECT и INSERT ровно в 22 таблицы и две RLS-политики на каждую (44). У роли нет BYPASSRLS, UPDATE или DELETE. Повторный запрос подтвердил отсутствие USAGE у `anon`, `authenticated`, `service_role`.
8. Проверка в транзакции: временно разрешили администратору `SET ROLE`, от имени `sefirot_ingest` вставили команду и прочитали её. `ROLLBACK` удалил запись и временный GRANT; после запроса `teams=0`, `audit_logs=0`, право администратора на SET ROLE вернулось к прежнему значению. Это проверяет права и RLS, но не сетевую аутентификацию.
9. После миграции Security Advisor вернул пустой список. Performance Advisor по-прежнему даёт только 14 INFO о неиспользуемых индексах: таблицы пусты.

## Границы

- SQLite остаётся авторитетным локальным журналом. Команда `sync-supabase` реализует одностороннюю сверку всех 22 таблиц, только INSERT, полное сравнение записей, проверку исходной цепочки аудита и атомарный откат при конфликте. Она покрыта локальными тестами с симуляцией сбоев. Реальная команда через сеть **не запускалась**, поскольку у роли ещё нет пароля/LOGIN и сертификат CA не предоставлен; работающий облачный feedback loop этим не доказан.
- Фактические строки матчей и ставок не загружались. Пробная транзакция была отменена; нагрузочные измерения и сверка реальной синхронизации не проводились. Облачный журнал пока пустой.
- Клиентские роли не должны получать права через дополнительные GRANT или изменение списка доступных Data API схем без пересмотра модели доступа. Не помещать секреты Supabase в GitHub, браузерный клиент или отчёт.
- Отсутствуют внешняя независимая экспертиза и положительная проверка прибыльности модели. Денежная политика SEFIROT остаётся закрытой.
- Полный снимок ограничен 100 000 строками и требует памяти пропорционально размеру SQLite. Успешная копия зависит от сохранности локального журнала; хеш-цепочка не защищает от злонамеренного администратора и потери последнего хвоста событий без внешнего запечатанного якоря.

## Активация владельцем (вне Git)

Отдельный администратор должен задать роли `sefirot_ingest` право `LOGIN` и сильный пароль **в частном канале**, скачать CA сертификат проекта в Database Settings → SSL Configuration и передать программе Session pooler DSN (порт 5432), включая `sefirot_ingest.<project-ref>` как пользователя. Используйте переменные окружения `SEFIROT_SUPABASE_DB_DSN` и `SEFIROT_SUPABASE_CA`. Программа навязывает `sslmode=verify-full`. Не используйте учётную запись `postgres` или ключ `service_role`: клиент специально отклоняет соединение не от `sefirot_ingest`.

SQL для **новой** базы: сначала `schema/supabase_core.sql`, затем `schema/supabase_ingest_role.sql`. Для уже созданного проекта оба файла повторно применять нельзя: миграция роли уже внесена. Для быстрой блокировки выгрузки администратор может вернуть роли `NOLOGIN` и отозвать её пароль. Загрузка не открывает денежную политику и не синхронизирует записи в обратном направлении.

Справка анализатора: https://supabase.com/docs/guides/database/database-linter?lint=0008_rls_enabled_no_policy и https://supabase.com/docs/guides/database/database-linter?lint=0005_unused_index .
