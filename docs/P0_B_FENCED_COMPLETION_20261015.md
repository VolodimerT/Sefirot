# P0-B: сохранение квитанции при потере подтверждения

База этапа: unified draft #56, `3414d932c0f4b2a82c75ab6e7cea866fc21e9feb`.
Работа относится к очереди и транспорту; `src`, модель, Policy, исходные записи,
протокол и прежние отчёты не изменяются. Только SYNTHETIC / RESEARCH_ONLY.

## Подтверждённые ошибки

На изолированном PostgreSQL старый RPC `sefirot_chat_complete` отклонил второе
сохранение идентичного уже записанного результата. Старый worker также мог
завершить RUNNING job после её повторного захвата другой попыткой: RPC не
проверял номер попытки. Ни один провайдер при воспроизведении не вызывался.
Предыдущий запрет повторного provider fetch остаётся обязательным.

## Исправление

- Worker передаёт `probe_complete` с UUID и целым номером захваченной попытки.
  Отсутствующая/неверная попытка останавливает обработку до исполнения и записи.
- Новый узкий `sefirot_probe_complete` проверяет вид job, состояние, номер попытки,
  исследовательские флаги, соответствие endpoint/params исходной очереди,
  ограничение размера и последовательность частичного batch до первой ошибки.
  Успешное исполнение разрешено только попытке 1. Попытки 2/3 не вызывают API.
- Старый completion отвергает sports_probe; fallback отсутствует. Только
  service_role может выполнить новый RPC; прямого доступа к таблицам не получает.
  SECURITY DEFINER использует пустой search_path и полные имена объектов.
- Идентичный терминальный результат возвращает прежнее подтверждение без UPDATE.
  Любая подмена payload/error/status и запоздавший номер попытки отклоняются.
  Relay и worker проверяют UUID и номер в подтверждении.
- Для этой операции worker делает максимум две попытки сохранения одного уже
  вычисленного результата: одна исходная и один повтор. Допустимы потеря связи,
  HTTP 500/502/503/504, повреждение обёртки ответа; 401/403/409/422/429 и ошибки
  валидации не повторяются. Никакого повтора claim, fetch, checkpoint или
  legacy completion. Коды и текст ошибок очищены от upstream body/URL/ключей.

## Проверки и пределы

Общий SQL fixture выполняется обязательным PostgreSQL WASM тестом и отдельным
native PostgreSQL 16 тестом. Существующие 18 SQL / 12 relay групп сохранены;
добавлены 10 SQL / 6 relay групп. Терминальный replay проверяется триггером,
запрещающим UPDATE, а не только совпадением timestamp внутри транзакции.
Сквозной локальный HTTP тест обрывает подтверждение ПОСЛЕ commit: provider stub
вызван один раз, completion два раза; restart сохраняет оригинальный packet и
проверяемые хэши. Искусственные квитанции не подтверждают provider origin.

Это восстановление потерянного подтверждения, а не обещание exactly-once между
внешним API и БД. Если процесс погиб до сохранения ответа, отсутствующая квитанция
не восстанавливается новым платным запросом и не реконструируется из хэша.
Такое событие остаётся явным блокером ручной проверки. Новый RPC защищает
машинную очередь; он не является криптографической аттестацией провайдера и
не проверяет исходные HTTP bytes. Существующий verifier архива остаётся необходим.

## Развёртывание не выполнено

Кандидат SQL находится в существующем `schema/supabase_chat_situation.sql`.
CLI Supabase 2.81.3 в рабочей среде не установился (exit 1); новая миграция с
выдуманным номером не создавалась. Этот пакет уже содержит CREATE объектов
предыдущего этапа, поэтому повторять весь файл на существующей hosted БД нельзя.

До отдельно разрешённого rollout необходимы reviewed incremental SQL diff,
выключенный бюджет, отсутствие in_flight, остановка/дренирование claims и
согласованные SQL + relay + worker. Смешивание старого worker с новым SQL
завершение probe блокирует; обратного небезопасного fallback нет. Проверка
живого контура и план возврата совместимых версий остаются отдельным этапом.
Никаких hosted SQL, изменения секретов, деплоя, включения бюджета или новых
платных запросов этот этап не выполняет. PASS / stake=0 остаются в силе.
