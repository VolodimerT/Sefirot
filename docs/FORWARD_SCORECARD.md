# Forward scorecard: первый шаг после сравнительного обзора

Добавлен read-only отчёт всей заранее назначенной API-выборки. Он не
обучает модель, не подбирает пороги и не создаёт validation/approval.
Вероятности читаются из оригинальных seals; старую сборку не переподписывает.

```powershell
py -3 sefirot.py --db data/research.sqlite forward-scorecard PLAN_ID --output data/scorecard.json --text
py -3 sefirot.py --db data/research.sqlite forward-scorecard PLAN_ID --as-of "2026-10-05T06:00:00Z" --output data/scorecard-at-cutoff.json
```

Для Linux/macOS замените `py -3` на `python3`. Существующий output не
перезаписывается. Отсутствующая БД не создаётся. При `--as-of` будущие
результаты, задания и прогнозы не участвуют в отчёте; будущий cutoff запрещён.

## Что оценивается

Каждый матч плана сохраняется в знаменателе: NO_SEAL, пропущенное окно,
непригодный/revised seal, неизвестное API-происхождение, ожидаемый результат,
VOID и успешно оценённый результат. Последняя причина попытки capture
показывается отдельно. Семь контрактов одного матча не считаются семью
независимыми матчами. Метрики не смешиваются между лигами, профилями и
контрактами; агрегированного сертификата на все 7 рынков нет.

Прогноз должен совпадать с планом: build/model/policy/calibrator, fixture,
пул рынков, назначенная роль и предматчевое время. Synthetic, reconstructed,
revised и дополнительные прогнозы не оцениваются. Требуется сохранённое
forward-capture задание, связывающее API-квитанции, sports hash и prediction.
Capture-start может предшествовать seal, а запись задания — следовать за ним.
Для результата нужен точный FINISHED FT payload в связанном API-source
задании плана. Строка `API_FOOTBALL_V3` в ручном source недостаточна.
VOID сохраняется в coverage без фиктивного проигрыша.

Архивный code_hash допускается для чтения, если probability/settlement
model_hash совместим. Отчёт не продолжает старый collector новой сборкой;
capture/settle архивного плана по-прежнему требуют оригинальный build.

## Метрики и ориентиры

Для raw и base вероятностей: multiclass Brier (половина суммы квадратов),
log loss (явный clip 1e-15), ECE и фиксированные 10 reliability bins по
WIN/PUSH/LOSS. Небольшие calibration bins шумны; ECE не является денежным
допуском, а Brier сам по себе не выделяет качество калибровки из остальных
составляющих качества прогноза.

Два простых ориентира:

1. Neutral: вероятность возврата из original raw, оставшаяся масса поровну
   между WIN/LOSS. Это слабый технический baseline, не рыночная линия.
2. Frozen-input climatology: частоты исходов контракта только на ID истории,
   зафиксированных в original model.used_history, с Laplace +1 на возможные
   исходы. У push-free контрактов PUSH остаётся 0. Нет полной истории — нет
   исторического baseline; отсутствие данных не подменяется сильной моделью.

Разность Brier с historical reference считается на общей парной подвыборке.
Исторические записи после original sports.as_of запрещены. Наблюдения,
которых нет в frozen used_history, не добавляются после знания результата.
Исходные истории могут быть неполными/неравномерными, поэтому этот ориентир
не объявляется точной силой лиги или достаточным доказательством преимущества.

Совместимого зарегистрированного API market reference пока нет:
market_reference=null, NO_BOUND_API_MARKET_REFERENCE. Котировки не
выдумываются и не подставляются задним числом. Следующий этап — заранее
сохранять complete no-vig линии БК с receipt и проверять качество на тех же
матчах. Это ещё не реализовано данным отчётом.

целостности, архивный build, отдельные лиги/профили, frozen history,
