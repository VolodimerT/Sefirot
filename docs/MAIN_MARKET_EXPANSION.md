# Сефирот: основные рынки и замороженная сетка

Дата: 04.10.2026, Киев. База — CORE 2.4.2, оптимизированная рабочая ветка
`core242-version-audit`, commit `cb07ebb7cece7a383141c5b7244294065eac2f28`.

## Реализовано

Адаптер The Odds API раньше импортировал только 1X2. Теперь он импортирует
полные линии 1X2, DNB, двухсторонней форы, тотала, ОЗ и индивидуального
тотала. Поддержаны дополнительные линии форы, тотала и индивидуального
тотала. Запрашивается один указанный букмекер; список API-рынков задан явно.

| Семейство CORE | API market key | Условие импорта |
|---|---|---|
| 1X2 | h2h | HOME/DRAW/AWAY одной линии |
| DNB | draw_no_bet | HOME/AWAY; ничья — PUSH |
| HANDICAP | spreads, alternate_spreads | HOME/AWAY с противоположными форами |
| TOTAL | totals, alternate_totals | OVER/UNDER одного порога |
| BTTS | btts | Yes/No |
| TEAM_TOTAL | team_totals, alternate_team_totals | Over/Under одного порога и точного description команды |
| DOUBLE_CHANCE | Нет добавленного API-контракта | Без котировки; цену не выводить из 1X2 |

Каждый импорт проверяет точные команды, kickoff, event_id, sport_key,
подтверждение REGULATION_90, полную пару/тройку исходов, возраст цены и её
получение после seal. Квартальные линии отклоняются существующим контрактом.
Неполные, дублированные, устаревшие или противоречивые линии фиксируются в
`rejected_lines`; неполученные контракты — в `missing_candidates`.
Повтор featured/alternate сохраняет featured-линию целиком без выбора
лучшей цены из двух источников. Underround-линии консервативно отклоняются.

Новый `market-grid` создаёт 50 фиксированных контрактов из сохранённого
спортивного snapshot. Он воспроизводит исходные семь кандидатов и модель;
цены в этот расчёт не входят. Каждая сетка привязана к исходному prediction,
code/model/policy hashes и времени заморозки. Расчёты соседних линий не
изменяют исходный прогноз и не записывают новое решение в журнал.

| Семейство | Сетка | Количество |
|---|---|---:|
| 1X2 | HOME, DRAW, AWAY | 3 |
| Двойной шанс | 1X, X2, 12 | 3 |
| DNB | HOME, AWAY | 2 |
| Фора | HOME/AWAY × −1.5, −1, −0.5, 0, +0.5, +1, +1.5 | 14 |
| Тотал | OVER/UNDER × 1.5, 2, 2.5, 3, 3.5 | 10 |
| ОЗ | YES, NO | 2 |
| ИТ | HOME/AWAY × OVER/UNDER × 0.5, 1, 1.5, 2 | 16 |
| Всего | Фиксировано до просмотра цен | 50 |

`compare-grid` использует файл API-котировок с соседней квитанцией
`.receipt.json`. Квитанция связана с hash котировок, grid_hash, fixture,
bookmaker и временем получения. Подмена или случайное смешение файлов
отклоняются. Квитанция — метаданные локального адаптера, не цифровая
подпись провайдера; пользователь, переписавший весь комплект, может
подделать эти метаданные. Система не заявляет криптографическую аттестацию API.

Сравнение сохраняет ВСЕ 50 контрактов, включая неполучившие цену. Для цены
показывает implied P, raw/base EV, границы EV калибровки, raw stress EV,
рыночное сравнение, raw P(LOSS) и примеры проигрышных счетов. Набор top-score
losses не является полным набором ветвей и не доказывает tactical fit.
Tactical fit берётся только из исходного snapshot; public trap остаётся
UNASSESSED без данных публичных ставок. Raw-сетка согласована с общей
массой счёта; отдельные рыночные калибровки могут нарушать согласованность
соседних линий, поэтому они показаны отдельно и не объявлены единой
откалиброванной массой счёта.

## Использование

Сначала получить реальный prematch snapshot через существующий
API-Football-путь, capture и проверить readiness. `<ID>` — сохранённый
prediction_id; надписи-заглушки заменяются настоящими ID провайдера.

```powershell
py -3 sefirot.py --db data/sefirot.sqlite readiness <ID> --text

# Импорт поддержанных семейств исходного семирынкового пула:
py -3 sefirot.py --db data/sefirot.sqlite fetch-odds <ID> --sport soccer_epl --event-id <EVENT_ID> --bookmaker <BOOKMAKER_KEY> --rules-confirmed --main-markets --output data/main-quotes.json

# Исследование соседних линий: сетку создать ДО запроса их цены:
py -3 sefirot.py --db data/sefirot.sqlite market-grid <ID> --output data/grid.json
py -3 sefirot.py --db data/sefirot.sqlite fetch-odds <ID> --sport soccer_epl --event-id <EVENT_ID> --bookmaker <BOOKMAKER_KEY> --rules-confirmed --grid data/grid.json --output data/grid-quotes.json
py -3 sefirot.py --db data/sefirot.sqlite compare-grid data/grid.json data/grid-quotes.json --output data/grid-comparison.json
```

Старый вызов `fetch-odds` без новых флагов сохраняет режим 1X2.
Выходные файлы не перезаписываются. `--main-markets` и `--grid` взаимоисключаемы.
Список рынков провайдера не гарантирует их наличие в данной лиге/БК.
Запрос дополнительных рынков может потреблять больше существующей API-квоты;
новая подписка не приобретается. Без ключей `API_FOOTBALL_KEY` и
`SEFIROT_ODDS_API_KEY` реальная сеть не проверяется.

## Границы и следующий эксперимент

BASELINE_V1/STRICT, research-policy-v3 и денежный пул максимум из семи
кандидатов — без изменений. Расширенная сетка имеет RESEARCH_ONLY, класс D,
stake=0, monetary_permission=false. Даже положительный EV не открывает BET.
Не добавлены LIVE, догон, экспрессы, builder, угловые, фолы, удары или ЖК.
Для малых рынков нужны собственные API-данные, settlement-контракты,
модели и проверка; для ЖК дополнительно строгий Referee Gate.

Приоритеты следующего измеримого цикла:

1. **Реальный API-проход.** Получить на будущих матчах sports → capture →
   grid → API quotes → comparison; сохранить пропуски, payload hashes и
   квоту. Критерий: воспроизводимый комплект без ручных цен/фиктивных FACT.
2. **Проверка всей процедуры выбора.** До первого будущего матча зафиксировать
   текущую сетку, правило отбора, даты, лиги, источники и метрики. Сравнивать
   семь исходных кандидатов с пятьюдесятью на тех же матчах; считать все
   пропуски. Группировать неопределённость по матчам, поскольку соседние
   рынки зависимы. Старый просмотренный TEST не использовать для настройки.
3. **Проверка согласованности калибровки.** Измерять нарушения монотонности
   соседних тоталов/ИТ и несовпадение эквивалентных DNB/форы 0. После этого
   сравнивать отдельные bins с challenger общей массой счёта на новом периоде.
4. **Очередь полезных данных.** У каждой блокировки хранить источник,
   следующее действие, срок и признак способности изменить допуск;
   CALIBRATION/HOLDOUT не пытаться лечить повторным запросом коэффициента.

Изменения CLI/адаптера/исследовательского отчёта меняют code_hash.
Вероятностные зависимости не менялись, поэтому model_hash сохранён.
Это не перенос разрешений: старые seals/денежные approvals остаются
связанными с прежней сборкой; новая CLI откажет импортировать цены
к prediction с несовпадающим code_hash/policy_hash. Архивный replay выполнять
исходной сборкой. Не сливать в main до ранее согласованного holdout.
