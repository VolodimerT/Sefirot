# P0-B: пакет обновления и безопасная остановка

База инженерной проверки: `4f30dc8bb09bfd76c13958492da8455e6e4e9b57`,
draft PR #56. Документ и SQL готовят операцию к ревью. Они не разрешают её
исполнение. На этом этапе hosted SQL, deploy/restart, бюджет и ключи не менялись.
Новых provider API calls нет. RESEARCH_ONLY / PASS / stake=0.

## Подтверждённая разница схем

Read-only наблюдение Supabase от 15.10.2026 16:09:26 UTC: в ограничении kind
есть `stake_snapshot` и `sports_probe`; нового probe RPC ещё нет. Бюджет выключен
(QUOTA_STOP), in_flight отсутствует, PENDING/RUNNING по 0. Это снимок, перед
любой разрешённой операцией его требуется повторить. Секретные значения не читались.

Полный `schema/supabase_chat_situation.sql` заменяет kind constraint без
`stake_snapshot`. На заполненной тестовой базе такой пакет отклонён CHECK при
существующей записи этого вида. На пустой он мог бы незаметно сузить контракт.
Поэтому полный CREATE-пакет не является hosted upgrade. Новая точечная миграция
не меняет таблицы/ограничения, сохраняет этот kind и все имеющиеся записи.
Сохранение kind не означает, что unified worker уже умеет его обрабатывать:
`stake_snapshot` отсутствует в его SAFE_KINDS; соответствующий producer нельзя
возобновлять без отдельной проверки контракта и доступа Stake.

## Подготовленные SQL

- `supabase/migrations/20261015161027_probe_completion_fence.sql` — только
  существующий bridge. Имя создано командой CLI `migration new`.
- `supabase/review_only/20261015161311_park_probe_queue.sql` — остановка очереди,
  намеренно вне обычной цепочки миграций. Имя тоже создано CLI.
- `schema/probe_rollout_manifest.json` — пути и ожидаемые SHA-256 тел функций.

CLI 2.81.3 получен из официального GitHub release; архив проверен по digest
`2938de97c4ee1d15de4affe9bfdac3dd665bc57d264f69101482133798f40e0a`.
Это локальный инструмент; login, link и hosted push не выполнялись. Каталог
Supabase не содержит восстановленную историю production и не служит bootstrap.

Миграция требует postgres, существующую закрытую очередь с RLS, отсутствие
PENDING/RUNNING, выключенный бюджет без in_flight. Блокировки таблиц сохраняют
эти условия в транзакции; lock timeout 3 секунды и statement timeout 15 секунд
ограничивают ожидание. При несоответствии операция целиком откатывается.

Она проверяет владельца, search_path, сигнатуры, права и известные хэши функций.
Неизвестная реализация, новые overloads или чужой доступ требуют ручного ревью.
Исходное тело completion копируется без изменения в owner-only функцию закрытой
схемы. Публичный wrapper сперва блокирует обход sports_probe/situation, затем
делегирует остальные виды исходному коду. Это сохраняет прежнюю реализацию,
вместо предположения, что синтетическая фикстура точно повторяет production.
Приватный delegate недоступен PUBLIC/anon/authenticated/service_role.

Новый probe RPC совпадает с уже проверенным canonical телом кандидата. Идентичный
повтор миграции разрешён, подмена backup/RPC/прав отклоняется. Главное:
**после установки право claim у service_role отозвано**. Даже ошибочно оставшийся
старый worker не должен забирать задачи. Унаследованное разрешение, мешающее
остановке, приводит к отказу всей миграции. Бюджет не включается.

## Порядок после отдельного разрешения владельца

1. Зафиксировать exact SHA кандидата, tree, CI, SQL digest и наблюдаемую версию
   SQL/relay/worker. Проверить backup исходного canonical snapshot и его checksum
   через существующий verifier. Не публиковать ledger, токены и построчную опись.
2. Сохранить выключенный бюджет, остановить worker и producers, включая внешние
   enqueue-клиенты. Дождаться отсутствия PENDING/RUNNING/in_flight; неизвестные
   попытки не сбрасывать и не выдавать за новые. При неопределённом receipt — STOP.
3. Повторить read-only SQL/ACL/body-hash проверки и выполнить только reviewed delta.
   Убедиться, что claim действительно запрещён service_role; проверить прежние
   записи и kind constraint. `NOTIFY pgrst` обновляет schema cache после commit.
4. Обновить согласованные relay и worker, проверить точные исходники и runtime.
   Нельзя заменить deployed credential-hash конфигурацию пустым шаблоном из Git.
   Секреты сохраняются; их значения в отчёт не выводить. Python Render 3.14.3
   пока не проверен текущим CI 3.11/3.13 — этот разрыв остаётся стоп-условием
   полного rollout, пока поддерживаемый runtime не выбран и не проверен.
5. В отдельной разрешённой тестовой среде повторить authenticated transport,
   stale lease, потерю ack, archive/restart и отказ legacy completion. Наличие
   функции само по себе не доказывает правильную версию relay/worker.
6. Только после успешной проверки всех реально разрешённых kinds и отдельного
   разрешения возобновить claim. Само обновление его не возобновляет. Бюджет
   остаётся выключенным. Новое платное окно требует другого явного разрешения.

Операция возобновления — точечный `GRANT EXECUTE` для
`public.sefirot_chat_claim()` роли service_role после всех проверок, а не rerun
всего SQL-пакета. В этом задании она на hosted БД не выполняется. Рекомендуется
отдельно сохранить факт и время разрешения, SHA версий и результаты проверки.

## Совместимость и откат

| Состояние | Результат |
|---|---|
| Старые SQL/relay/worker | Старый completion не проверяет probe lease; не возобновлять provider research |
| Новый delta, любой worker до resume | Claim запрещён, новых задач worker не получает |
| Старый relay + новый worker после resume | Новый action не поддержан; такая комбинация запрещена |
| Новый relay + старый SQL после resume | Новый RPC отсутствует; такая комбинация запрещена |
| Новый SQL + старый worker после resume | Legacy probe completion запрещён; такая комбинация запрещена |
| Все согласованы и проверены | Только RESEARCH_ONLY; платный fetch всё ещё запрещён выключенным бюджетом |
| Safe park | Claim и новый probe completion запрещены; fencing и исходные записи сохранены |

При сбое сначала остановить worker/producers, оставить бюджет выключенным и
сверить отсутствие незавершённых операций. Затем отдельный park SQL отзывает
claim/probe EXECUTE у service_role, проверяет фактический запрет и сохраняет
wrapper, приватный delegate и все records. Повтор park безопасен. Нельзя
переименовать delegate обратно, открыть старый unfenced completion, удалять
квитанции, менять attempts, переочередить job ради повторного provider fetch
или сбрасывать дневную квоту. При активной работе park откажет: это стоп-сигнал
для расследования, а не повод обойти проверку.

Возврат старого runtime допустим только при остановленной очереди и выключенном
бюджете. Возврат старого SQL-контракта не входит в безопасный откат. Повтор delta
после park сохраняет запрет claim; самостоятельного возобновления нет.
Exactly-once между внешним API и БД не обещается: crash до записи receipt остаётся
явной неопределённостью, без нового оплачиваемого запроса или выдуманного архива.

## Проверки и ограничения доказательств

Обязательный WASM runner проверяет 33 группы: populated upgrade, 14 вариантов
отказа (до/после обновления), interruption rollback, сохранность исходного тела
completion и квитанций, повтор delta/park, запрет старого completion и ошибочного
полного CREATE-пакета, применение после fresh unified schema. Прежние 18 SQL /
12 relay / 10 probe SQL / 6 probe relay групп сохранены.

Отдельный native PostgreSQL 16 выполняет те же rejection fixtures, исходные
10 probe SQL-групп и upgrade/park на своей пустой локальной базе. Общий прогон
не заменяет этот native job; локальный advisor и exact-head CI отмечаются
отдельно в итоговом отчёте. Это собственные синтетические тесты, без внешнего
человека-аудитора и без проверки production-перехода.

Официальный доступ Stake, реальные котировки, полная PREMATCH цепочка,
независимый HOLDOUT и преимущество модели остаются неподтверждёнными. Данный
пакет не даёт финансового разрешения и не закрывает автоматически P0/Issues.
