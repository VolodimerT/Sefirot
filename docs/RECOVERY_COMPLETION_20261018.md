# Завершение доступной подготовки, 18.10.2026

Исходный PR56 HEAD: `d64af6c2c381e82b325b1f1164202de74deb84d3`.
Новый код продолжает тот же PR и не включает production deployment.

Два дефекта воспроизведены на исходном HEAD. Во-первых, `sync_archive` после
1000 private archive reads возвращал incomplete, но не принимал курсор.
Следующий запуск опять читал первые 1000 пакетов: более поздние по хешу пакеты
оставались недоступны независимо от числа запусков. Во-вторых, настоящая CLI
на повреждённом файле SQLite завершалась traceback и кодом1 вместо безопасной
диагностики отказа. Тесты до ремонта подтверждают оба случая.

Теперь ограниченный sync возвращает `next_after` и принимает `after`; CLI имеет
`--after` и `--limit`. Продолжение разрешено только из уже импортированного
пакета того же source Repository. Курсор не является временной границей:
после завершения scan сбрасывается, чтобы следующий цикл нашёл поздние INSERT
с меньшим хешем. Сбой не отменяет committed originals; повторная страница
дедуплицируется и сохраняет первое время знания. Не добавлены новые таблицы,
движки, сервисы, автоматические API retries или бюджетные разрешения.
Ошибки SQLite CLI теперь дают код2 и фиксированное безопасное сообщение.

Отдельные regression tests проверяют несколько страниц с малым лимитом,
новый меньший хеш, потерю ответа после committed страницы, чужой/невалидный
курсор, реальный CLI на повреждённой базе и private CLI output/продолжение.
Это изолированные проверки: они не изображают доступ к облачному архиву,
который ещё не установлен. Настоящие8 пакетов пилота18Oct проверяются отдельно
в локальном существующем source Repository, без новых upstream запросов.

Остаются внешние ограничения. Разрешённый deployment HEAD=c558486a отличается
от текущего PR56; решение PASS/NO DEPLOY. Production Render остаётся42e25ccc,
autoDeploy=no, Free web service: polling не предотвращает idle spin-down.
Новая sports_archive SQL/RPC, relay/Gateway/worker opt-in и owner-only planner
подготовлены, но production migration/activation/schedule не установлены.
Для постоянно работающего ежедневного сбора нужно отдельно согласовать точный
новый SHA, существующий coordinated rollout/rollback и постоянно доступный
consumer/scheduler. Новые платные сервисы и keepalive не создавались.
